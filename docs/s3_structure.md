# S3 Structure

## Overview

This project stores scraper outputs in Amazon S3 using a consistent structure designed to support:

* Historical snapshots
* Latest/current datasets
* Run logs
* Future aggregation and indexing
* Role-based access control

The S3 bucket currently in use is:

```text
event-scrape-data
```

---

## Top-Level Access Structure

Data is grouped by access level:

```text
public/
internal/
restricted/
```

### Access levels

* `public/` → safe for broad access
* `internal/` → internal operational data
* `restricted/` → sensitive data requiring tighter control

---

## Standard Folder Pattern

Each access level uses the same internal structure:

```text
{access_level}/
  raw/{dataset}/
  latest/{dataset}.json
  logs/{dataset}/
  index/
```

---

## Folder Purposes

### `raw/`

Stores historical dataset snapshots.

Each run writes a new timestamped file and never overwrites previous runs.

Example:

```text
restricted/raw/staff-time-off/2026-04-02T11-39-44Z.json
```

Purpose:

* audit trail
* history tracking
* debugging
* comparison between runs

---

### `latest/`

Stores the current version of a dataset.

Each run overwrites the existing file.

Example:

```text
restricted/latest/staff-time-off.json
```

Purpose:

* current source of truth
* simplest file for UI or API consumption
* stable path for downstream systems

---

### `logs/`

Stores structured execution logs for each scraper run.

Each run writes a timestamped JSON log file.

Example:

```text
restricted/logs/staff-time-off/2026-04-02T11-39-44Z.json
```

Purpose:

* operational monitoring
* troubleshooting
* audit of successful and failed runs
* record counts and output locations

---

### `index/`

Reserved for future collated datasets and aggregated output files.

Examples may include:

```text
public/index/master.json
internal/index/master.json
restricted/index/master.json
```

Purpose:

* consolidated datasets
* CloudFront/UI-ready files
* search/index support
* combined multi-source data views

## Naming Rules

### Dataset names

Use lowercase kebab-case:

* `staff-time-off`
* `public-events`
* `trade-events`
* `historical-sales`

### Timestamp format

Use UTC timestamps in this format:

```text
YYYY-MM-DDTHH-MM-SSZ
```

Example:

```text
2026-04-02T11-39-44Z
```

### File extensions

All dataset files and logs are saved as:

```text
.json
```

## Why This Structure Exists

This layout is designed to support:

1. Historical retention without overwriting prior runs
2. A stable “latest” file for downstream use
3. Structured logging for troubleshooting
4. Clean separation by sensitivity/access level
5. Future UI/API consumption via CloudFront and aggregation jobs

---

## Design Notes

### Why keep both `raw` and `latest`?

* `raw` preserves history
* `latest` provides current state

### Why keep logs in S3?

* easier run auditing
* easier remote troubleshooting
* supports future operational dashboards

### Why separate by access level?

Even though each record contains an `access` object, S3-level grouping provides:

* cleaner structure
* easier policy control later
* simpler future API/UI design
* reduced risk of accidental exposure

---

## Future Direction

The long-term goal is to support a collated dataset layer for CloudFront and UI search.

Expected future additions:

* `index/master.json`
* combined public event feeds
* searchable date/location datasets
* role-aware dataset delivery
* aggregation scripts that merge multiple scrapers into one index
